## Known release blocker: OCI alias provenance

The OCI publication workflow inherited from `image-template` published aliases from the same build through independent pushes, producing different registry digests (`same-run-different-registry-digests`).

Evidence from container run `32388901082` at main SHA `95e9faaedf06f972a3d9e37bfb65f84ffdc21064`:

| Alias | Registry digest |
|---|---|
| `latest` | `sha256:0ddb80b83618853883969d3de29df74306b6d4a3154372f62a7eb3f607af6a18` |
| `latest-95e9faa` | `sha256:1e03b576f9475e4f6d8846fde499662a3de40637ade916fa4d21d62dd10b9140` |

The first and subsequent pushes produced different manifests because of the handling of `ostree.components`; only the final digest was signed. This does not invalidate the already built and tested RC1 ISO, but it prevents the current state from being called Final. OCI publication must be corrected before a canonical RC2 or Final.

## Release policy and next steps

RC1 is a baseline for physical validation, not Final. New functional changes should be delivered through OCI/bootc; an ISO does not need to be rebuilt for every change.

Next steps:

1. Install and test RC1 on the ThinkPad T495.
2. Correct OCI publication so aliases preserve canonical provenance.
3. Validate the new canonical OCI.
4. Update the T495 through bootc.
5. Decide whether the next release is RC2 or Final.
6. Generate a new ISO only when a new installation baseline is useful for new installations.
